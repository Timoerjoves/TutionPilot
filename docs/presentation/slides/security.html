About 1 minute 15. Security is 30 percent of the score. We replaced the hand-kept list of payees with digital signatures. Top row, the university invoice. TuitionPilot trusts one root key. The root signs a certificate for each university that names its bank account and SWIFT, and there is a signed list of revoked certificates. The university signs each invoice with its own key. The agent checks every link: the certificate is signed by the root and not revoked, the invoice signature is valid, the bank details equal the certificate, and the printed text matches the signed data. So if someone changes the bank account on the invoice, the signature breaks. Bottom row, the parent's approval. The parent's browser makes its own key, which cannot be exported; only the public half is registered. The first parent device needs the PIN; any later device needs the PIN and a signature from an already enrolled parent device. To approve, the browser recomputes the plan hash itself and signs the approval for that exact plan. The policy engine checks that signature before any payment. The agent never has the parent's key, so it cannot forge an approval or change the plan afterwards. The tiers are the same as before, and tier 3 now needs the PIN and the device signature. Tier 4 is never allowed. The signature code is plain Python following the RFC, with nothing to install, and it is checked against the RFC's test vectors and a signature made by the browser. And the model still has no payment tool at all.
